    LLM은 어떻게 답을 만드는가?¶

    모델에 질문을 보내고 첫 글자가 보이기까지 왜 시간이 걸릴까요? 답이 시작된 뒤에도 왜 한 번에 끝나지 않고 조금씩 나타날까요? 이 장은 입력이 토큰으로 바뀌고, 모델이 입력을 읽는 prefill을 거쳐, 출력 토큰을 하나씩 만드는 decode까지를 따라갑니다.

    이 장은 Modular의 How does an LLM work?를 번역·재구성했습니다. 기준 원문은 저장소 커밋 07e93d6입니다. 이 장에서 말하는 일반적인 LLM은 별도 표시가 없으면 다음 토큰을 예측하는 decoder-only Transformer를 뜻합니다.

    토큰은 무엇이고 왜 나누는가?¶

    모델은 문장을 문자 그대로 계산하지 않습니다. 먼저 토크나이저(tokenizer)가 문장을 작은 단위인 토큰(token)으로 나누고, 각 토큰을 정수 ID로 바꿉니다. 토큰은 단어 하나일 수도, 단어의 일부나 문장부호일 수도 있습니다. 토크나이저와 어휘 목록은 모델마다 다릅니다.

    예를 들어 안녕하세요, 오늘 날씨는?을 넣으면 토크나이저는 이를 여러 토큰 ID로 바꿉니다. 정확한 분할과 ID는 모델의 토크나이저에 따라 달라지므로, 어떤 모델의 토큰 수를 다른 모델에 그대로 적용하면 안 됩니다.

    모델은 현재까지의 토큰을 보고 다음 토큰 하나의 점수를 계산합니다. 선택된 토큰을 입력 끝에 붙이고 같은 과정을 반복합니다. 멈춤 토큰이나 최대 출력 길이 같은 종료 조건에 도달하면 새 토큰들을 다시 읽을 수 있는 텍스트로 변환합니다.

    한국어판 보충 설명: 토큰 수와 비용

    API가 입력·출력 토큰 수로 과금한다면 문자의 개수보다 토크나이저가 만든 토큰 수가 중요합니다. 같은 뜻의 문장이라도 언어와 표기 방식에 따라 토큰 수가 달라질 수 있습니다. 비용이나 최대 문맥 길이를 계산할 때는 사용할 모델의 토크나이저로 세어야 합니다.

    모델 안에는 어떤 계산이 있는가?¶

    토큰 ID는 먼저 숫자 벡터인 임베딩으로 바뀝니다. 모델은 토큰의 순서를 알 수 있도록 위치 정보도 사용합니다. 벡터는 여러 Transformer 층을 지나면서 주변 토큰과의 관계를 반영하고, 마지막 층의 결과는 가능한 다음 토큰 각각의 점수인 logit으로 바뀝니다.

    위치 정보를 더하는 방법도 모델마다 다릅니다. 예를 들어 RoPE(Rotary Positional Embedding)는 attention 계산에서 위치를 표현합니다. 다음 토큰 후보는 모델의 어휘 목록(vocabulary)에 있는 토큰으로 한정되므로, 어휘가 크면 마지막 점수 계산층도 커집니다.

    한 Transformer 층을 단순화하면 두 일을 합니다.

    1. Self-attention은 현재 토큰이 앞의 어떤 토큰 정보를 참고할지 계산합니다.
    2. Feed-forward network는 각 토큰의 표현을 변환합니다.

    이 층을 여러 번 지나면 입력 문장과 이미 생성한 토큰을 바탕으로 다음 토큰의 점수를 얻습니다. 점수를 확률로 바꾸고 하나를 고르는 과정은 뒤의 샘플링 절에서 다룹니다.

    Attention은 무엇을 참고하는가?¶

    문장에 같은 단어가 여러 의미로 쓰이면 주변 문맥을 봐야 합니다. Attention은 토큰마다 다른 토큰의 정보를 얼마나 가져올지 가중치를 계산합니다.

    각 층은 토큰의 현재 표현에서 세 벡터를 만듭니다.

    • Query(Q): 지금 어떤 정보를 찾는가?
    • Key(K): 이 토큰이 어떤 정보와 연결되는가?
    • Value(V): 연결됐을 때 실제로 가져올 내용은 무엇인가?

    현재 토큰의 Q와 참고할 토큰들의 K를 비교해 점수를 만들고, softmax로 합이 1인 가중치로 바꿉니다. 그 가중치로 V를 합쳐 현재 토큰의 표현을 갱신합니다. 간단한 한 개 attention head의 식은 다음과 같습니다.

    \[ \operatorname{Attention}(Q,K,V) =\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V \]

    여기서 \(d_k\)는 K 벡터의 차원입니다. 식을 외우는 것보다 Q와 K는 어느 토큰을 참고할지 정하고, V는 실제로 가져올 정보라는 구분이 중요합니다.

    한국어판 보충 설명: Attention과 사실 확인

    Attention이 특정 토큰을 많이 참고했다는 사실만으로 모델이 그 문장을 이해하거나 답이 사실이라고 결론 내릴 수는 없습니다. 이 계산은 다음 토큰을 예측하는 내부 과정입니다. 출력의 정확성은 별도로 평가해야 합니다.

    미래 토큰을 왜 가리는가?¶

    다음 토큰을 예측할 때 현재 위치가 아직 생성되지 않은 미래 토큰을 보면 답을 미리 보는 셈입니다. Causal mask는 각 위치가 자기 자신과 이전 위치의 토큰만 참고하도록 attention 점수를 제한합니다. 미래 위치의 점수를 사실상 사용할 수 없게 만들어 가중치가 0이 되게 합니다.

    이 가림은 여러 입력 토큰을 병렬 처리하는 학습과 prefill에서 중요합니다. 한 번에 여러 위치를 계산하더라도 앞의 위치가 뒤의 내용을 보지 못해야, 나중에 한 토큰씩 생성할 때의 조건과 맞습니다. 길이가 다른 문장을 배치로 묶기 위해 추가한 의미 없는 padding 토큰도 mask로 제외할 수 있습니다.

    한국어판 보충 설명: decode에서는?

    일반적인 한 토큰씩의 decode에서는 아직 미래 토큰 자체가 존재하지 않습니다. 따라서 prefill에서처럼 여러 미래 위치를 가리는 문제가 적지만, 구현에 따라 attention mask를 계속 사용할 수 있습니다.

    관련 자료

    • Modular 원문: Attention mask — causal mask와 padding mask.
    • Attention Is All You Need — autoregressive decoder의 masking.

    Prefill과 decode는 무엇이 다른가?¶

    입력을 읽는 단계와 답을 이어 쓰는 단계는 작업의 모양이 다릅니다.

    Prefill: 입력 전체 읽기¶

    토크나이저가 만든 입력 토큰을 모델에 넣습니다. 모델은 입력 전체를 알고 있으므로 각 위치를 병렬 계산할 수 있습니다. 각 Transformer 층에서 Q, K, V를 계산하고, 뒤의 생성 단계가 다시 쓸 KV cache를 만듭니다. 긴 입력은 이 단계의 시간이 늘어나기 쉽습니다.

    첫 토큰이 사용자에게 도착하기까지의 TTFT에는 prefill 외에도 대기열과 네트워크 시간이 포함됩니다. 따라서 TTFT가 길다는 사실만으로 prefill 계산이 유일한 원인이라고 단정하면 안 됩니다.

    Decode: 출력 이어 쓰기¶

    입력 처리가 끝나면 모델은 다음 토큰을 하나 고릅니다. 새 토큰을 붙이고, 또 다음 토큰을 고릅니다. 토큰을 고르는 순서는 앞 토큰에 의존하므로 한 요청의 전체 출력을 보통 한 번에 병렬 생성할 수 없습니다.

    이 반복은 최대 출력 토큰 수에 도달하거나, 종료 토큰이 나오거나, 지정한 중지 문자열 같은 조건에 걸리면 멈춥니다. 생성한 토큰 ID는 다시 사람이 읽는 텍스트로 변환합니다. 스트리밍 API라면 완료 전에도 만들어진 부분을 순서대로 전송할 수 있습니다.

    이때 과거 토큰의 K와 V를 다시 계산하지 않도록 KV cache에서 읽습니다. 그 대가로 토큰이 늘수록 cache가 커지고 GPU 메모리를 차지합니다. Decode의 체감 속도는 토큰 사이의 간격인 ITL이나 평균 TPOT로 살핍니다.

    단계 입력 상태 주로 보는 성능 자주 문제 되는 자원
    Prefill 요청의 입력 토큰 전체를 알고 있다. TTFT의 일부 긴 입력에 필요한 계산량
    Decode 앞 토큰의 결과를 보고 다음 하나를 만든다. ITL·TPOT 반복적인 가중치·KV cache 읽기

    두 단계를 같은 GPU에서 실행하면¶

    여러 요청이 몰린 서버에서는 한 요청의 prefill과 다른 요청의 decode가 GPU 시간을 경쟁합니다. 긴 입력을 처리하는 동안 이미 답을 받고 있던 요청의 다음 토큰이 늦어질 수 있습니다. 이를 줄이기 위해 스케줄러를 조정하거나 두 단계를 다른 작업자로 분리하는 설계도 있습니다.

    한국어판 보충 설명: 계산 병목과 메모리 병목

    Prefill을 늘 계산 병목, decode를 늘 메모리 병목으로 단정하지 마세요. 이는 흔한 경향을 설명하는 단순화이며 모델 크기, 배치, 문맥 길이, 하드웨어에 따라 달라집니다. 실제 병목은 입력 길이와 동시 요청 수를 기록한 뒤 측정해야 합니다.

    문맥 창과 KV cache는 어떻게 다른가?¶

    문맥 창(context window)은 한 요청에서 모델이 참고할 수 있는 토큰의 범위입니다. 대화를 이어갈 때 이전 메시지를 입력에 다시 포함하면 모델이 앞의 내용을 볼 수 있습니다. 최대 길이를 넘으면 오래된 메시지를 빼거나 요약하는 등의 처리가 필요합니다.

    KV cache는 한 번의 추론 실행 중 이미 계산한 K와 V를 저장한 메모리입니다. 문맥 창은 모델에 보이는 토큰 범위이고, KV cache는 그 범위를 처리하며 만든 계산 결과의 저장 공간입니다. 둘을 같은 뜻으로 쓰면 메모리 문제를 이해하기 어렵습니다.

    원문은 Llama 3 8B의 8K 토큰 시퀀스가 FP16 KV 캐시를 약 1 GB 쓸 수 있다는 예를 듭니다. 이는 모델 구조와 KV 헤드 수에 따른 사례값이며 모든 8B 모델에 적용되는 상수가 아닙니다. 가중치가 GPU에 올라가더라도 활성 요청마다 캐시가 추가되므로, 실제 동시 요청 수는 GPU 메모리 예산에 의해 제한됩니다. 캐시를 블록으로 관리하는 PagedAttention, 공통 입력을 재사용하는 prefix caching, 일부를 다른 메모리로 옮기는 offloading은 각각 다른 방식으로 이 부담을 다룹니다.

    한국어판 보충 설명: 요청 사이의 재사용

    일반적인 새 요청에서는 이전 대화를 다시 보내더라도 입력을 새로 처리합니다. 같은 앞부분의 KV cache를 요청 사이에 재사용하려면 서버가 prefix caching 같은 기능을 지원하고 재사용 가능한 조건이 맞아야 합니다. 대화 기록을 API에 다시 보내는 행위 자체가 KV cache의 영구 저장을 뜻하지는 않습니다.

    모든 LLM이 토큰을 하나씩 만들까?¶

    이 장의 설명은 널리 쓰이는 자기회귀형 decoder-only 모델을 기준으로 합니다. BERT 같은 encoder-only 모델은 분류나 표현 추출에 쓰이며 같은 방식으로 긴 답을 토큰별 생성하지 않습니다. T5 같은 encoder-decoder 모델은 입력을 읽는 encoder와 출력을 생성하는 decoder를 구분합니다.

    원문은 텍스트를 반복적으로 다듬는 diffusion LLM도 소개합니다. 이런 모델은 자기회귀형 모델과 생성 절차가 다릅니다. 다만 특정 제품의 속도나 품질 주장을 모든 diffusion LLM에 일반화할 수는 없습니다. 이 책의 뒤쪽 서빙·캐시 설명은 기본적으로 자기회귀형 모델을 대상으로 합니다.

    원문에는 Mercury와 Gemini Diffusion이라는 초기 사례가 나옵니다. 두 사례는 텍스트를 한 토큰씩 이어 붙이는 방식 외에도 연구와 제품 실험이 있음을 보여 줍니다. 원문의 특정 배속·우수성 표현은 비교 조건에 따라 달라지므로 여기서는 보편적 성능 수치로 옮기지 않았습니다.

    모델 계열 대표적인 사용 방식 이 장의 prefill·decode 설명 적용
    Encoder-only 분류·검색 표현 그대로 적용되지 않는다.
    Encoder-decoder 입력 변환·생성 decoder의 순차 생성에는 일부 적용된다.
    Decoder-only 채팅·코드 생성 이 장의 기본 모델이다.
    Diffusion 기반 텍스트 모델 반복적 결과 개선 생성 방식에 따라 별도 설명이 필요하다.

    다음 토큰은 어떻게 고르고 왜 느릴까?¶

    모델은 다음 단어를 바로 내놓지 않고 어휘의 각 토큰에 대한 점수를 만듭니다. Temperature는 이 점수에서 만든 확률 분포의 뾰족함을 조절합니다. Greedy 방식은 가장 높은 확률의 토큰을 고르고, top-k와 top-p는 후보 집합을 제한한 뒤 선택합니다. 같은 모델이라도 설정에 따라 다른 답이 나올 수 있습니다.

    추론이 느려지는 주된 이유는 다음과 같습니다.

    1. 출력 토큰을 앞 토큰에 의존해 순서대로 만들기 때문에 한 요청의 생성 단계에 병렬화 한계가 있습니다.
    2. Decode 때 모델 가중치와 커지는 KV cache를 반복해 읽습니다.
    3. 입력이 길거나 동시 요청이 많으면 prefill 계산과 대기열 시간이 늘 수 있습니다.

    따라서 느리다는 말만으로 최적화 방법을 고를 수 없습니다. 성능 지표 장의 TTFT·TPOT·E2EL을 먼저 구분하고, 요청 길이와 서버 부하를 함께 적어 두세요.

    핵심 정리¶

    • 토크나이저는 문장을 모델이 읽는 토큰 ID로 바꿉니다.
    • Attention의 Q와 K는 참고할 토큰을 정하고, V는 가져올 정보를 제공합니다.
    • Causal mask는 현재 위치가 미래 토큰을 미리 보지 못하게 합니다.
    • Prefill은 입력을 읽고 KV cache를 만들며, decode는 그 cache를 쓰면서 출력 토큰을 이어 만듭니다.
    • 문맥 창은 모델에 보이는 범위이고 KV cache는 계산 결과의 저장 공간입니다.
