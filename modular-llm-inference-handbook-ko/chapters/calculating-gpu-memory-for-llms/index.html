    LLM 서빙에 필요한 GPU 메모리는 어떻게 계산할까?¶

    7B 모델의 가중치가 14 GB라면 16 GB GPU에서 서비스를 운영할 수 있을까요? 모델을 한 번 불러오는 것과 여러 사용자의 긴 요청을 안정적으로 처리하는 것은 다릅니다. 이 장에서는 GPU 메모리(VRAM)를 가중치, KV 캐시, 실행 여유분으로 나눠 예산을 세웁니다.

    이 장은 Modular의 GPU 메모리 계산 원문을 번역·재구성했습니다. 기준 원고는 커밋 07e93d6입니다. 별도로 더한 계산법은 한국어판 보충 설명으로 표시합니다.

    가중치는 얼마나 차지할까?¶

    매개변수(parameter)는 모델이 학습한 숫자입니다. 8B 모델은 대략 80억 개의 매개변수를 가집니다. 숫자 하나를 16비트로 저장하면 2바이트, 8비트로 저장하면 1바이트가 필요합니다. 따라서 가장 단순한 추정은 다음과 같습니다.

    \[\text{가중치 바이트} \approx \text{매개변수 수}\times\frac{\text{가중치 비트 수}}{8}\]

    예를 들어 7B 모델의 FP16 가중치는 약 14 GB입니다. 여기서 GB는 \(10^9\)바이트이고, 운영체제와 GPU 도구에서 흔히 쓰는 GiB는 \(2^{30}\)바이트입니다. 같은 14 GB는 약 13.0 GiB입니다. 단위를 섞으면 작은 GPU에서 용량 판단이 달라집니다.

    정밀도를 낮추는 양자화는 가중치 용량을 줄일 수 있습니다. 하지만 실제 파일에는 스케일, 제로 포인트 같은 보조 정보가 붙고, 연산용 버퍼가 추가될 수 있습니다. 4비트라고 해서 실제 서빙 메모리가 FP16의 정확히 4분의 1이라고 가정하면 안 됩니다. 지원하는 데이터 형식과 커널도 GPU·서빙 엔진에 따라 다릅니다.

    실행 중 메모리는 왜 더 필요할까?¶

    모델은 답을 만들면서 이전 토큰의 attention 정보를 KV 캐시에 저장합니다. 이는 다음 토큰을 만들 때 이전 내용을 매번 다시 계산하지 않도록 돕습니다. 입력이 길고 동시에 실행 중인 요청이 많을수록 캐시는 커집니다.

    한국어판 보충 설명: KV 캐시의 상한 추정

    한 요청이 길이 \(T\)인 시퀀스를 처리한다고 가정하면, 보통의 자기회귀 Transformer에서 KV 캐시의 대략적인 크기는 다음과 같습니다. \(L\)은 층 수, \(H_{kv}\)는 KV 헤드 수, \(D\)는 헤드 차원, \(B\)는 KV 원소의 바이트 수입니다.

    \[\text{KV 캐시 바이트} \approx 2\times L\times H_{kv}\times D\times T\times B\]

    앞의 2는 Key와 Value를 각각 저장하기 때문입니다. 동시 요청이 \(C\)개이고 길이가 모두 같다면 결과에 \(C\)를 곱합니다. 실제 길이가 다르면 요청별 길이의 합을 쓰는 편이 낫습니다. 모델 구조, KV 양자화, 캐시 공유·블록 할당에 따라 실제 점유량은 달라집니다.

    이 밖에 임시 활성값, 연산 작업 공간, 프레임워크 할당량, CUDA graph 등이 메모리를 씁니다. 원문의 가중치 × (1 + 오버헤드 비율)은 빠른 초기 추정에는 편하지만, 긴 문맥과 많은 동시 요청을 평가할 때는 KV 캐시를 별도로 계산하는 편이 안전합니다.

    원문의 간편식은 매개변수 수를 십억 개 단위로 \(P\), 가중치 비트 수를 \(Q\), 추가 메모리 비율을 \(O\)라고 둘 때 다음과 같습니다. 결과의 단위는 대략 GB입니다. \(O\)는 고정된 자연 상수가 아니라 요청 길이·동시성에 따라 바뀌는 가정값입니다.

    \[\text{서빙 메모리(GB)}\approx P\times\frac{Q}{8}\times(1+O)\]

    직접 계산해 보기: 어떤 값이 한계를 바꿀까?¶

    아래 계산기는 단일 GPU에서 모델 전체와 각 요청의 KV 캐시를 함께 보관하는 단순한 상황을 가정합니다. 입력한 문맥 길이는 각 동시 요청이 사용할 수 있는 길이의 상한으로 취급하므로, 결과는 실제 평균 점유량보다 높을 수 있습니다. 반대로 실행 여유분을 작게 넣으면 실제 필요량보다 낮게 나옵니다.

    GPU 메모리 예산 계산기

    예를 들어 기본값인 8B·16비트 가중치·32층·KV 헤드 8개·8,192토큰·동시 요청 1개에서는 가중치가 약 14.9 GiB, KV 캐시가 1.0 GiB, 여유분 3 GiB를 포함한 합계가 약 18.9 GiB입니다. 동시 요청을 8개로 바꾸면 KV 캐시만 8 GiB로 늘어납니다. 가중치는 그대로여도 용량이 부족해질 수 있습니다.

    한국어판 보충 설명: 계산기 결과의 한계

    이 계산기는 가중치 보조 데이터, 메모리 단편화, CUDA graph, 연산 중 피크 메모리, 모델 병렬화, 일부 층만 활성화하는 MoE 구조를 정확히 모델링하지 않습니다. GPU 용량과 비교한 결과는 배포 가능 판정이 아닌 1차 예산입니다. 선택한 모델·서빙 엔진·실제 요청 길이로 부하 시험을 하세요.

    원문은 정밀도 형식이 GPU마다 다르게 지원된다고도 강조합니다. 예를 들어 어떤 GPU에서 FP8 형식을 저장할 수 있다는 것과 해당 형식의 연산을 하드웨어로 가속할 수 있다는 것은 다릅니다. 모델 파일의 형식, 엔진의 커널, GPU 세대를 함께 확인해야 합니다.

    메모리가 부족하면 무엇을 조정할까?¶

    먼저 실제로 부족한 부분을 확인하세요. 가중치가 큰 경우에는 모델 크기나 정밀도를 바꾸거나 모델을 여러 GPU에 나눠야 합니다. KV 캐시가 큰 경우에는 최대 문맥 길이, 동시 요청 수, KV 정밀도, 캐시 관리 방식을 검토합니다. 여유분이 부족하면 같은 모델이 로딩되더라도 피크 부하에서 메모리 부족 오류가 날 수 있습니다.

    바꾸는 값 주로 줄어드는 메모리 함께 확인할 점
    더 작은 모델 가중치, 대개 KV 캐시 작업 품질과 필요한 문맥 길이
    가중치 양자화 가중치 품질, 커널 지원, 추가 보조 데이터
    최대 문맥 길이 축소 요청별 KV 캐시 상한 긴 문서와 대화의 처리 가능 여부
    동시 요청 제한 KV 캐시 총량 대기 시간과 처리량
    KV 캐시 양자화·블록 관리 KV 캐시 지원 여부, 품질·속도 영향

    핵심 정리¶

    • 가중치 크기는 매개변수 수와 저장 정밀도로 먼저 추정합니다.
    • GB와 GiB는 다른 단위입니다. GPU 용량과 같은 단위로 비교합니다.
    • KV 캐시는 길이와 동시 요청 수에 따라 커집니다.
    • 실행 여유분까지 합쳐야 서빙 메모리의 1차 예산이 됩니다.
    • 계산기로 후보를 좁힌 뒤 실제 트래픽과 엔진으로 검증합니다.
