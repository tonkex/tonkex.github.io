    요청을 묶으면 왜 더 빨리 처리할 수 있을까?¶

    서버에 질문이 세 개 들어왔습니다. 하나씩 순서대로 처리할까요, 잠시 모아 함께 처리할까요? 배칭(batching)은 여러 요청을 GPU의 한 번의 작업 묶음에 넣는 방법입니다. 모델 가중치를 읽는 비용을 여러 요청이 나눌 수 있지만, 묶음을 기다리는 시간이나 짧은 요청의 완료 시점도 달라집니다.

    이 장은 Modular의 정적·동적·연속 배칭 원문을 번역·재구성했습니다. 기준 원고는 커밋 07e93d6입니다. 예시와 주의점 중 별도 설명은 한국어판 보충 설명으로 표시합니다.

    정적 배칭: 정해진 수가 모일 때까지 기다리기¶

    정적 배칭은 요청이 정해진 수만큼 모이면 한 묶음으로 시작합니다. 크기가 3이라면 첫 요청은 세 번째 요청이 올 때까지 기다립니다. 트래픽이 드문 시간에는 그 대기가 길어질 수 있습니다.

    한 묶음 안에서도 답변 길이는 다릅니다. 요청 A가 2토큰, B가 6토큰을 만들면 A는 일찍 끝나도 묶음 전체가 B의 여섯 번째 토큰까지 유지될 수 있습니다. 원문이 지적하는 문제는 시작 전 대기와 긴 요청 때문에 묶음이 오래 유지되는 현상입니다.

    한국어판 보충 설명: 구현마다 반환 시점은 다릅니다

    정적 배칭을 쓴다는 사실만으로 짧은 요청의 결과를 무조건 마지막 요청과 동시에 반환한다고 단정할 수는 없습니다. 여기서는 원문이 비교하는 단순한 고정 묶음 모델을 설명합니다. 실제 엔진의 스트리밍·완료 처리 방식은 따로 확인하세요.

    동적 배칭: 인원 제한과 출발 시각 함께 두기¶

    동적 배칭은 최대 크기와 짧은 대기 창을 함께 둡니다. 묶음이 가득 차면 즉시 시작하고, 가득 차지 않아도 정해진 시간이 지나면 모인 요청으로 시작합니다. 버스가 정원에 차거나 출발 시각이 되면 떠나는 모습과 비슷합니다.

    요청이 드문 시간에도 끝없이 기다리지 않는다는 장점이 있습니다. 대기 창을 길게 잡으면 GPU 작업을 더 많이 묶을 기회가 생기지만 첫 응답은 늦어질 수 있습니다. 너무 짧으면 배치를 거의 만들지 못합니다. 동적 배칭도 묶음을 언제 만들지에 관한 방식이므로, 생성 도중 빈 자리에 새 요청을 넣는 연속 배칭과는 다릅니다.

    관련 자료

    • Modular 원문: 동적 배칭 — 대기 창과 묶음 크기의 관계.
    • NVIDIA Triton 동적 배처 문서 — 동적 배처의 설정 개념.

    연속 배칭: 끝난 요청의 자리를 다시 쓰기¶

    LLM은 출력 토큰을 하나씩 생성합니다. 연속 배칭(continuous batching)은 토큰 생성 반복마다 실행 중인 요청을 살피고, 끝난 요청의 자리에 대기 중인 새 요청을 넣습니다. 원문에서는 이를 in-flight batching이라고도 부릅니다.

    예를 들어 GPU가 요청 두 개를 함께 처리하고 A가 먼저 끝났다면, B가 계속 생성하는 동안 C가 다음 반복부터 합류할 수 있습니다. GPU는 B가 모두 끝날 때까지 C를 기다리게 할 필요가 없습니다. 다만 새 요청의 입력을 처리할 메모리와 연산 예산이 있어야 하며, 실제 스케줄러는 우선순위와 토큰 예산도 고려합니다.

    요청 자리 바뀌는 모습

    동시에 실행할 수 있는 자리는 2개, A와 B가 먼저 도착하고 C는 기다린다고 가정합니다. 버튼을 눌러 출력 토큰 생성 단계를 진행하세요.

    한국어판 보충 설명: 단순화된 도해

    위 도해는 A가 두 단계, B가 네 단계, C가 두 단계 걸린다는 학습용 시나리오입니다. 실제 엔진에서는 prefill과 decode의 비용이 다르고, 요청의 길이와 메모리 상태도 수시로 달라집니다. 이 그림은 완료한 요청의 자리를 언제 다시 쓰는지만 보여 줍니다.

    연속 배칭이 처리량을 높일 가능성은 크지만, 동시 요청을 무조건 많이 넣으면 각 요청의 토큰 간격(ITL)이 늘 수 있습니다. 배치 방식의 평가는 지연 시간과 Goodput을 함께 봐야 합니다.

    긴 입력이 끼어들면: 청크 단위 prefill¶

    새 요청의 긴 입력을 처리하는 prefill은 한 번에 많은 계산을 합니다. 그동안 이미 답을 출력 중인 요청의 decode가 멈추면 사용자는 글자가 한동안 나오지 않는다고 느낄 수 있습니다.

    청크 단위 prefill(chunked prefill)은 긴 입력을 여러 토큰 묶음으로 나눕니다. 스케줄러는 일부 입력 청크와 기존 요청의 다음 토큰 생성을 번갈아 또는 함께 배치할 수 있습니다. 앞부분의 KV 캐시를 이어 쓰므로 각 입력 토큰은 이전 토큰 정보를 계속 참조합니다. 첫 출력 토큰은 마지막 입력 청크까지 처리한 뒤에 나옵니다.

    청크가 작으면 기존 요청의 decode를 끼워 넣을 기회가 늘지만, 새 요청의 첫 토큰까지 시간이 늘거나 오버헤드가 커질 수 있습니다. 청크가 크면 새 요청의 입력을 효율적으로 처리할 수 있지만 기존 스트리밍 요청이 더 오래 기다릴 수 있습니다. 모델, GPU, 입력 길이 분포, SLO에 맞춰 값을 정해야 합니다.

    원문은 엔진마다 청크 크기를 표현하는 설정이 다르다는 점도 보여 줍니다. 아래는 기준 원문 시점의 명령 예이며, 실제 실행 전에는 설치한 버전의 도움말과 모델 사용 조건을 확인해야 합니다.

    # MAX: 배치의 입력 토큰 예산과 최소 청크 크기
max serve --model meta-llama/Llama-3.1-8B-Instruct \
  --enable-chunked-prefill \
  --max-batch-input-tokens 8192 \
  --chunked-prefill-min-chunk-size 512

# vLLM: 한 스케줄링 반복의 토큰 예산
vllm serve --model meta-llama/Llama-3.1-8B-Instruct \
  --enable-chunked-prefill \
  --max-num-batched-tokens 8192

# SGLang: 한 prefill 청크의 최대 토큰 수
sglang serve --model-path meta-llama/Llama-3.1-8B-Instruct \
  --chunked-prefill-size 8192

    같은 8192라도 배치 전체의 토큰 예산인지 개별 청크의 상한인지 다릅니다. 옵션 이름을 숫자만 보고 옮기지 마세요.

    길이가 다른 입력은 어떻게 한 묶음에 넣을까?¶

    입력 길이가 [1024, 1000, 50, 20]토큰이라면 모두 1024칸짜리 사각형으로 맞추는 패딩(padding)이 간단합니다. 빈 칸은 attention mask로 가리지만, 구현에 따라 불필요한 계산이나 메모리 사용이 생길 수 있습니다.

    Ragged tensor는 실제 토큰들을 붙여 저장하고 각 요청의 길이·시작 위치를 별도 메타데이터로 기록하는 방식입니다. 패딩을 줄일 수 있지만 커널과 스케줄러가 가변 길이를 다룰 수 있어야 합니다. PagedAttention은 KV 캐시를 블록 단위로 관리하여 이런 길이 차이가 큰 요청을 함께 처리하는 데 도움을 줍니다.

    원문의 FAQ에서 등장하는 PAD, <pad>, 또는 정수 0 같은 표기는 토크나이저마다 다릅니다. 실제 0번 토큰이 항상 패딩이라는 뜻은 아닙니다. 패딩을 넣은 위치는 attention mask 등으로 알려 주어 모델이 유효한 입력과 구별하도록 합니다.

    핵심 정리¶

    • 배칭은 여러 요청이 모델 가중치 읽기 비용을 나눠 쓰게 합니다.
    • 정적 배칭은 정해진 수를 기다리고, 동적 배칭은 크기 또는 대기 시간으로 출발합니다.
    • 연속 배칭은 토큰 생성 중 끝난 요청의 자리를 새 요청에 넘깁니다.
    • 청크 단위 prefill은 긴 입력이 기존 출력 흐름을 오래 막지 않도록 돕습니다.
    • 처리량만 보지 말고 TTFT, ITL, Goodput을 함께 비교합니다.
