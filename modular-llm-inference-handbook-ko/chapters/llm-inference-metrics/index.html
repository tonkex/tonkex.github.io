    추론 성능 지표: 사용자가 느끼는 속도를 어떻게 읽을까?¶

    채팅 서비스가 초당 토큰을 많이 만들어도, 사용자가 첫 문장을 오래 기다리면 빠른 서비스라고 느끼기 어렵습니다. 반대로 첫 단어는 즉시 보여 주지만 뒤의 문장이 느리게 나오거나 요청이 자주 실패한다면 숫자 하나로는 문제를 찾을 수 없습니다. 이 장에서는 한 요청의 기다림, 서버 전체의 처리량, 목표를 지킨 처리량을 차례로 구분합니다.

    이 장은 Modular의 Key metrics for LLM inference를 번역·재구성했습니다. 기준 원문은 저장소 커밋 07e93d6입니다. 별도로 더한 설명은 한국어판 보충 설명으로 표시합니다.

    지연 시간: 한 요청에서 어디를 기다리는가?¶

    지연 시간(latency)은 요청을 보낸 뒤 응답을 받기까지 걸린 시간입니다. LLM은 답을 한꺼번에 보내기도 하고, 생성되는 토큰을 순서대로 보내기도 합니다. 스트리밍 응답에서는 첫 토큰과 마지막 토큰의 도착 시간을 따로 재면 원인을 더 잘 찾을 수 있습니다.

    • TTFT(Time to First Token): 요청을 보낸 시점부터 첫 출력 토큰을 받을 때까지의 시간입니다. 대기열, 입력 처리, 첫 토큰 생성, 네트워크 시간이 포함될 수 있습니다.
    • E2EL(End-to-End Latency): 요청부터 마지막 출력 토큰을 받을 때까지의 전체 시간입니다.
    • 생성 구간 시간: 첫 토큰 이후 마지막 토큰까지의 시간입니다. E2EL − TTFT로 계산합니다.
    • TPOT(Time per Output Token): 생성 구간에서 토큰 사이의 평균 간격입니다. 출력 토큰이 \(N\)개라면 토큰 사이 간격은 \(N-1\)개입니다.
    • ITL(Inter-Token Latency): 연속된 두 토큰 사이의 개별 간격입니다. 한 요청의 ITL을 평균하면 TPOT가 됩니다.
    \[ \text{TPOT} = \frac{\text{E2EL}-\text{TTFT}}{N-1},\qquad N\ge2 \]

    예를 들어 첫 토큰이 80 ms에 도착하고 마지막 토큰이 2,200 ms에 도착했으며 출력이 220개라면, 생성 구간은 2,120 ms이고 간격은 219개입니다. TPOT는 약 9.68 ms/토큰입니다. TTFT와 TPOT는 각각 첫 반응과 그 뒤의 흐름을 보여 줍니다.

    직접 바꿔 보기: 지연 시간과 목표 달성

    아래 값은 실제 서버 측정치가 아닌 학습용 예시입니다. 숫자를 바꾸면 시간축과 TPOT가 갱신됩니다.

    첫 토큰 대기(TTFT) 이후 생성(E2EL − TTFT)

    시간축은 두 구간의 길이 비율을 표시합니다. 정확한 값은 바로 위 결과 문장을 읽어 주세요.

    같은 기준으로 네 요청을 평가하기

    요청TTFTE2EL목표 충족
    A80 ms2,200 ms
    B250 ms1,800 ms
    C100 ms3,500 ms
    D150 ms2,400 ms

    한국어판 보충 설명: 여러 요청의 평균

    요청마다 출력 길이가 다르면 평균 TPOT와 전체 ITL 평균은 같지 않을 수 있습니다. 요청별 TPOT를 평균하면 요청마다 같은 가중치를 줍니다. 전체 ITL을 합쳐 평균하면 토큰 간격마다 같은 가중치를 줍니다. 첫 토큰은 간격을 만들지 않으므로, 여러 요청의 전체 ITL 평균에서 분모는 각 요청의 \((N_i-1)\)을 더한 값입니다. 지표를 비교할 때 측정 도구가 어느 방식을 쓰는지 확인하세요.

    평균값만 보면 느린 일부 요청을 놓치기도 합니다. 중앙값(P50)은 절반의 요청이 그 시간 안에 끝난다는 뜻이고, P99는 99%의 요청이 그 시간 안에 끝난다는 뜻입니다. 예를 들어 P50 TTFT가 80 ms인데 P99 TTFT가 2초라면 대부분은 빠르지만 일부 사용자는 첫 토큰을 오래 기다립니다. P90·P95도 같은 방식으로 읽습니다.

    산술평균(mean)은 관측값을 모두 더해 요청 수로 나눈 값이라 매우 느린 요청 하나에도 크게 움직일 수 있습니다. 중앙값은 전형적인 사용자의 경험을, P99는 느린 끝부분의 경험을 보여 줍니다. 성능 표를 읽을 때는 평균 TTFT와 P99 TTFT처럼 같은 지표의 다른 분위수를 함께 보세요.

    지연 목표는 작업에 따라 달라집니다. 대화형 채팅은 첫 반응이 중요하고, 밤새 만드는 보고서는 전체 완료 시간과 비용이 더 중요할 수 있습니다. 특정 밀리초 숫자를 모든 서비스의 정답으로 삼지 마세요.

    처리량: 서버가 얼마나 많은 일을 끝내는가?¶

    처리량(throughput)은 일정 시간 동안 끝낸 일의 양입니다. 대기 시간을 재는 지연 시간과 달리, 여러 사용자의 요청을 함께 처리하는 서버의 용량을 봅니다.

    • RPS(Requests per Second)는 초당 완료한 요청 수입니다. 10초 동안 요청 40개를 끝냈다면 4 RPS입니다.
    • TPS(Tokens per Second)는 초당 처리한 토큰 수입니다. 입력 토큰을 읽는 속도인 입력 TPS와 출력 토큰을 생성하는 출력 TPS를 구분해야 합니다.

    긴 문서를 요약하는 요청은 입력 토큰이 많아 입력 TPS가 중요하고, 짧은 질문에 긴 답을 쓰는 챗봇은 출력 TPS가 더 중요할 수 있습니다. 벤치마크가 입력·출력을 합친 숫자만 제시한다면 어느 단계가 빨라졌는지 알아보기 어렵습니다.

    \[ \text{RPS} = \frac{\text{측정 구간에 완료한 요청 수}}{\text{측정 구간의 초}},\qquad \text{TPS} = \frac{\text{측정 구간에 처리한 토큰 수}}{\text{측정 구간의 초}} \]

    한국어판 보충 설명: 같은 RPS, 다른 부하

    짧은 인사말 100개와 긴 문서 요약 100개는 요청 수가 같아도 입력·출력 토큰 수가 크게 다릅니다. RPS만 비교하면 서버가 수행한 일을 오해할 수 있습니다. 모델, 입력 길이, 출력 길이, 동시 요청 수, 하드웨어를 함께 적어야 의미 있는 비교가 됩니다.

    배치를 키우면 여러 요청에서 모델 가중치를 함께 활용해 총 TPS가 오를 수 있습니다. 하지만 요청이 배치를 기다리는 시간이 늘거나 각 사용자의 토큰 간격이 길어질 수도 있습니다. 총 TPS가 좋아졌는지와 사용자가 더 기다리는지를 함께 봐야 합니다.

    TPS는 배치 크기, KV 캐시 메모리, 입력·출력 길이, GPU 계산량과 메모리 대역폭에도 좌우됩니다. 서로 다른 모델이나 하드웨어의 TPS를 비교할 때는 이 조건을 맞춰야 합니다. 동시 요청을 늘리면 총 TPS가 오르다가 자원 한계에 이르면 대기와 지연이 급증하거나 처리량이 떨어질 수 있습니다.

    Goodput: 목표를 지키며 얼마나 처리하는가?¶

    처리량이 높아도 사용자가 기다리기로 한 한도를 자주 넘기면 서비스 품질이 좋다고 할 수 없습니다. SLO(Service-Level Objective)는 서비스를 평가할 때 정한 목표입니다. 예를 들어 TTFT ≤ 200 ms와 E2EL ≤ 3,000 ms를 동시에 만족해야 한 요청이 목표를 지킨 것으로 셀 수 있습니다.

    Goodput은 이런 조건을 지키며 완료한 요청의 처리량입니다. 전체 처리량에서 목표를 어긴 요청을 제외합니다.

    원문의 예처럼 전체 요청의 95%가 TTFT 200 ms 미만이라는 목표는 측정 구간 전체의 SLO입니다. 아래 실습은 각 요청의 TTFT와 E2EL이 지정한 상한을 모두 만족하는지 판정한 뒤, 그 요청들의 처리량을 계산합니다. 서비스의 SLO 달성률과 요청 단위 Goodput은 관련되지만 같은 지표는 아닙니다.

    \[ \text{Goodput (요청/초)} = \frac{\text{측정 구간에 모든 SLO를 만족한 완료 요청 수}} {\text{측정 구간의 초}} \]

    위 실습의 기본값에서 요청 네 개 중 두 개가 두 목표를 모두 만족합니다. 이때 목표 달성률은 50%입니다. 네 요청을 10초 동안 처리했다고 가정하면 Goodput은 0.2 요청/초입니다. 달성률과 Goodput은 단위부터 다릅니다.

    한국어판 보충 설명: 측정 구간을 명시하기

    목표를 지킨 요청 수만 알면 달성률은 계산할 수 있지만 Goodput의 단위인 요청/초는 계산할 수 없습니다. 반드시 같은 관측 구간의 길이를 함께 기록해야 합니다. 목표의 부등호, 측정 시작·종료 시점, 스트리밍 여부도 함께 고정하세요.

    지연 시간과 처리량 중 무엇을 먼저 볼까?¶

    대화형 채팅에서는 첫 반응과 토큰이 이어지는 속도가 중요합니다. 긴 문서를 한꺼번에 만드는 작업에서는 전체 완료 시간과 비용이 더 중요합니다. 요청별 목표를 정한 온라인 서비스라면 Goodput이 핵심입니다.

    원문은 목표를 세 가지 관점으로 비교합니다. 총 처리량을 높이면 큰 배치와 공유 자원으로 GPU당 또는 전력당 처리 토큰 수를 늘릴 수 있지만 개별 사용자가 기다릴 수 있습니다. 개별 지연을 줄이려 작은 배치와 충분한 여유 자원을 두면 GPU 효율이 낮아질 수 있습니다. 실제 서비스는 요청의 우선순위와 SLO를 보며 둘 사이를 조정합니다. TPS/MW처럼 전력당 성능을 볼 때도 하드웨어와 측정 조건을 함께 적어야 합니다.

    상황 먼저 볼 지표 이유
    대화형 채팅 TTFT, 이어서 TPOT·ITL 첫 반응과 글이 나타나는 흐름이 보인다.
    긴 스트리밍 답변 TPOT·ITL, E2EL 첫 토큰 이후의 생성 시간이 길다.
    여러 단계를 거치는 에이전트 E2EL 다음 단계는 대개 이전 결과가 끝나야 시작한다.
    대량 오프라인 처리 입력·출력 TPS, 비용 개별 요청의 즉각적인 응답보다 총 처리량이 중요하다.
    지연 목표가 있는 서비스 Goodput, P95·P99 많은 요청을 처리하면서 느린 사용자도 줄여야 한다.

    배칭, GPU 자원, 모델 정밀도, 병렬화 방법을 바꾸면 이 지표 중 하나는 좋아지고 다른 하나는 나빠질 수 있습니다. 실험 전 같은 입력·출력 길이와 동시 요청 수를 고정하고, 어떤 목표를 지킬지 먼저 적어 두세요.

    조정할 수 있는 수단에는 배치 크기, 데이터·텐서·전문가 병렬화, FP8·FP4 같은 정밀도, prefill과 decode를 다른 작업자로 나누는 방식이 있습니다. 관리형 API에서는 이런 내부 설정을 직접 바꾸기 어렵지만, 자체 서빙에서는 실제 작업 부하에 맞춰 조정하고 그 비용도 직접 감당합니다.

    핵심 정리¶

    • TTFT는 첫 토큰까지, E2EL은 마지막 토큰까지의 시간을 잽니다.
    • TPOT는 첫 토큰 이후의 평균 토큰 간격이며, 출력 토큰이 \(N\)개면 간격은 \(N-1\)개입니다.
    • RPS는 요청 수, TPS는 토큰 수를 시간으로 나눈 값입니다. 입력·출력 TPS를 구분합니다.
    • Goodput은 정한 SLO를 지키며 완료한 요청의 초당 처리량입니다.
    • 평균만 보지 말고 P95·P99와 요청 길이, 동시 요청 수도 함께 확인합니다.
