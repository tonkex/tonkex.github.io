    모델을 서비스하려면 어떤 추론 프레임워크가 필요할까?¶

    모델 파일을 내려받았는데 여러 사용자의 요청을 안정적으로 처리하려면 무엇이 더 필요할까요? 모델을 한 번 실행하는 코드와 지속적으로 요청을 받는 서비스는 다릅니다. 추론 프레임워크는 모델 적재, 토큰 생성, 대기열·배칭, KV 캐시, 스트리밍과 API를 묶어 줍니다.

    이 장은 Modular의 추론 프레임워크 선택 원문을 번역·재구성했습니다. 기준 원고는 커밋 07e93d6입니다. 추가 해설은 한국어판 보충 설명으로 표시합니다.

    추론 프레임워크는 무엇을 하는가?¶

    추론 프레임워크는 가중치를 메모리에 적재하고, 입력을 토큰으로 바꿔 모델을 실행하며, 결과를 애플리케이션에 전달하는 소프트웨어 계층입니다. 런타임, 엔진, 백엔드, 모델 서버라는 이름도 쓰이지만 제품마다 범위가 다릅니다. 단순한 로컬 실행 도구에서 분산 서빙 플랫폼까지 같은 말로 부르기도 합니다.

    LLM은 출력 토큰을 순서대로 생성합니다. 여러 요청을 동시에 받을 때는 어떤 요청을 언제 실행할지 스케줄링하고, 이전 토큰의 정보를 담는 KV 캐시를 관리해야 합니다. 결과를 한꺼번에 보내는 대신 생성되는 대로 스트리밍할 수도 있습니다. 프레임워크는 이런 서비스 동작을 담당합니다.

    학습용 모델 코드를 그대로 서버에 두면 안 될까?¶

    PyTorch나 Transformers로 한 요청을 생성하는 실험은 충분히 가능합니다. 그러나 서비스에서는 동시에 들어오는 요청, 각기 다른 길이, 긴 문맥, 출력 스트리밍, 메모리 부족, 재시도와 장애까지 다뤄야 합니다. 학습 과정의 목표는 가중치를 업데이트하는 것이고, 추론 서비스의 목표는 정한 품질과 지연을 지키며 요청을 계속 처리하는 것입니다.

    원문은 배칭·스케줄링, KV 캐시, 스트리밍, 메모리 제한, API, 다중 GPU 실행을 추론 프레임워크의 주요 기능으로 정리합니다. 예를 들어 같은 GPU에서도 배칭 정책이 다르면 초당 처리한 토큰과 개별 사용자의 기다림이 달라질 수 있습니다. max-batch-size, GPU 메모리 사용률, 최대 문맥 길이 같은 설정은 엔진마다 이름과 허용값이 다릅니다.

    원문은 vLLM 및 MAX의 특정 모델·장비 벤치마크를 소개합니다. 이는 각각의 발표 조건에서 얻은 수치입니다. 모델 버전, 입력·출력 길이, 동시 요청 수, 지연 목표가 다르면 순위가 바뀔 수 있습니다. 후보를 고를 때는 동일한 장비와 작업 부하로 TTFT, TPOT, 처리량, 오류율, 메모리를 측정하세요.

    어떤 도구가 있고 무엇부터 확인해야 할까?¶

    원문은 서버용으로 vLLM, SGLang, MAX, LMDeploy, TensorRT LLM, TokenSpeed, Hugging Face TGI를, 로컬·엣지용으로 llama.cpp, MLC-LLM, Ollama를 소개합니다. 일부 엔진은 이미지·영상 생성 같은 다른 모델 계열도 지원합니다. 목록의 길이보다 다음 질문이 중요합니다.

    • vLLM은 GPU 서빙과 배칭·KV 캐시 관리에 초점을 둡니다. SGLang은 서빙 런타임과 모델 호출 기능을 함께 제공합니다. MAX는 Modular의 다중 장비 추론 도구입니다.
    • LMDeploy는 동시 요청과 양자화 지원을, TensorRT LLM은 NVIDIA GPU 최적화를 강조합니다. TokenSpeed는 에이전트형 작업의 스케줄링과 커널 구성에 초점을 둡니다.
    • TGI는 Hugging Face의 텍스트 생성 서버입니다. llama.cpp는 여러 장비에서 로컬 모델을 실행하며, MLC-LLM은 모델 컴파일과 다양한 장치 배포를 다룹니다. Ollama는 로컬 설치와 사용을 단순화합니다.
    • 원문은 텍스트 외의 예로 SGLang Diffusion, vLLM-Omni, MAX의 이미지·영상 생성 지원도 소개합니다. 지원 모델과 기능은 각 프로젝트의 현재 문서에서 확인하세요.

    라이브러리 모드와 서버 모드는 무엇이 다를까?¶

    라이브러리 모드는 애플리케이션 프로세스 안에서 엔진을 직접 실행합니다. 오프라인 배치나 평가 파이프라인처럼 호출자가 엔진을 직접 다루는 작업에 편합니다. vLLM의 LLM 클래스와 SGLang의 오프라인 엔진이 예입니다. 다만 GPU 메모리 부족이나 엔진 오류가 애플리케이션 프로세스에 영향을 줄 수 있습니다.

    서버 모드는 모델 실행을 별도 프로세스에서 운영하고 HTTP API로 요청을 받습니다. 여러 애플리케이션이 모델을 공유하거나, 요청 인증·라우팅·모니터링을 독립적으로 구성할 때 유용합니다. 네트워크 및 직렬화 비용이 추가되지만 애플리케이션과 모델 서버를 따로 배포·확장할 수 있습니다.

    # 원문의 라이브러리 모드 예: 설치와 모델 접근 권한이 필요합니다.
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct")
outputs = llm.generate(
    ["연속 배칭을 두 문장으로 설명해 줘."],
    SamplingParams(temperature=0.2, max_tokens=64),
)

    원문의 서버 예시는 MAX·vLLM·SGLang 명령과 OpenAI 호환 클라이언트를 나란히 보여 줍니다. 실제 명령·플래그와 API 지원 범위는 설치한 버전 및 모델에 따라 다릅니다. 특히 ‘OpenAI 호환’이라는 말만으로 모든 요청 필드와 응답 기능이 동일하다고 가정하지 마세요.

    # 원문의 서버 모드 예. 모델 접근 권한, 버전별 명령·포트 설정 확인이 필요합니다.
max serve --model meta-llama/Llama-3.1-8B-Instruct
vllm serve --model meta-llama/Llama-3.1-8B-Instruct
sglang serve --model-path meta-llama/Llama-3.1-8B-Instruct

    세 명령은 대안입니다. 한 번에 모두 실행하라는 뜻이 아닙니다. 서버가 준비되면 원문처럼 클라이언트의 base_url을 해당 서버 주소로 바꿔 호출할 수 있습니다. 예를 들어 vLLM의 기본 OpenAI 호환 서버 주소를 쓰는 경우는 다음과 같습니다.

    from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
response = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "연속 배칭을 두 문장으로 설명해 줘."}],
    temperature=0.2,
    max_tokens=64,
)
print(response.choices[0].message.content)

    한국어판 보충 설명: 예제의 연결 조건

    api_key="EMPTY"는 로컬 테스트 서버에서 쓰는 예시입니다. 외부에 서버를 노출할 때는 인증·접근 제어를 별도로 설정해야 합니다. MAX·SGLang의 포트와 API 주소도 실행 설정에 맞게 바꾸세요. 모델 접근 승인이 필요한 저장소라면 가중치 다운로드 권한을 먼저 확보해야 합니다.

    왜 한 조직에서 여러 런타임을 쓰기도 할까?¶

    서버의 큰 텍스트 모델, 노트북의 작은 모델, 모바일의 양자화 모델, 이미지 생성 모델은 장비와 요청 패턴이 다릅니다. 한 엔진이 모든 모델과 정밀도, API 기능을 같은 품질로 지원하지는 않습니다. 원문은 높은 처리량 서버, 로컬 실험, 엣지, 확산 모델에 서로 다른 런타임을 쓰는 예를 듭니다.

    런타임을 여러 개 쓰면 유연해지지만, 버전·로그·지표·인증·배포 방법이 늘어납니다. 호환되는 API 경계와 공통 평가 데이터를 유지하면 새 엔진을 시험하기 쉬워집니다. 그러나 API 모양이 같아도 토큰화, 샘플링, 도구 호출 결과가 같다는 보장은 없습니다.

    • Modular 원문: 모델 성능 벤치마크 — 비교 시나리오 설계.

    로컬 실험에서 분산 추론까지 어떻게 확장할까?¶

    처음에는 Ollama나 llama.cpp로 모델의 동작을 확인할 수 있습니다. 실제 사용자가 늘어나면 배칭·캐시·API와 관측성이 필요한 서버 엔진으로 옮길 수 있습니다. 모델이 한 GPU에 들어가지 않거나 여러 클러스터·리전으로 요청을 나누려면 모델 병렬화, 라우팅, 자동 확장, 장애 복구까지 설계해야 합니다.

    원문은 이 단계에서 분산 추론 플랫폼이 운영을 도울 수 있다고 설명합니다. 프레임워크 하나를 설치했다고 여러 리전의 용량 확보와 복구가 자동으로 해결되지는 않습니다. 반대로 작은 단일 서버 서비스에 복잡한 분산 플랫폼이 반드시 필요한 것도 아닙니다.

    원문 FAQ의 핵심 질문은 세 가지입니다. 모든 프레임워크가 모든 LLM을 지원하지 않으며, 분산 기능의 범위도 다르고, 초보자는 작은 로컬 실험에서 시작해 실제 트래픽으로 서버 엔진을 평가해야 합니다.

    핵심 정리¶

    • 추론 프레임워크는 모델 실행뿐 아니라 배칭, KV 캐시와 API를 맡습니다.
    • 선택 전에 모델·장비·정밀도·요청 기능의 지원 여부를 확인합니다.
    • 라이브러리 모드는 프로세스 안에서, 서버 모드는 별도 API 경계에서 실행합니다.
    • 공식 도구 문서의 현재 상태를 확인하고 원문의 성능 수치를 절대 순위로 읽지 않습니다.
    • 최종 후보는 실제 입력 길이, 동시성, 지연 목표로 부하 시험합니다.
