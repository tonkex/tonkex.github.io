    LLM 추론이란 무엇인가: API 뒤에서는 무슨 일이 일어날까?¶

    애플리케이션에서 모델 API에 질문을 보내면 잠시 뒤 답이 돌아옵니다. 이 사이에 모델이 입력을 읽고 다음 토큰을 계산하는 과정이 추론(inference)입니다. 사용자가 보낸 요청을 받아 모델에 전달하고, 여러 요청이 몰려도 응답을 돌려주는 일까지 합치면 서빙(serving)이라고 부릅니다.

    이 장은 Modular의 What is LLM inference?를 번역·재구성했습니다. 기준 원문은 저장소 커밋 07e93d6입니다. 별도로 더한 내용은 한국어판 보충 설명으로 표시합니다.

    추론은 고객 지원 챗봇의 답변, 긴 글의 요약과 문장 교정, 자연어 설명을 바탕으로 한 코드 생성, 여러 단계를 수행하는 AI 에이전트 등에서 쓰입니다. 응용 분야는 달라도 이미 학습된 모델에 입력을 넣고 출력을 계산한다는 점은 같습니다.

    아래 단계에서 하나를 선택하면 요청의 어느 부분이 추론이고 어느 부분이 서빙인지 볼 수 있습니다. 이 대화형 도해는 한국어판에서 새로 제작했습니다.

    한 요청의 이동 경로

    서버가 사용자 요청을 받아 대기열에 넣습니다. 이 단계는 서빙에 속합니다.

    서빙 단계

    추론 서버는 무엇을 하는가?¶

    추론 서버는 모델을 메모리에 올리고, 애플리케이션 요청을 받아, 계산 결과를 응답으로 돌려주는 프로그램입니다. 모델만 실행하는 Python 스크립트와 달리 여러 사용자가 동시에 들어오는 상황도 다룹니다.

    서버에는 보통 다음 기능이 필요합니다.

    • 요청 대기열: 한꺼번에 들어온 요청의 실행 순서를 관리합니다.
    • 배칭: 여러 요청을 함께 계산해 GPU를 효율적으로 사용합니다.
    • 스트리밍: 답 전체를 기다리지 않고 생성된 토큰부터 보냅니다.
    • 확장과 관측: 요청이 늘 때 서버를 늘리고, 지연·오류·자원 사용을 측정합니다.

    원문은 추론 서버와 추론 프레임워크라는 말을 실무에서 혼용하기도 한다고 설명합니다. 서버는 실행 중인 요청 처리 프로그램을, 프레임워크는 그 서버를 만들고 최적화하는 도구와 기능까지 가리킬 때가 많습니다. vLLM, SGLang, MAX, TensorRT-LLM처럼 두 역할을 함께 제공하는 도구도 있습니다.

    규모가 커지면 서버를 여러 복제본으로 늘리거나 줄이는 확장, 어느 복제본으로 요청을 보낼지 정하는 부하 분산, 모델 버전 교체와 상태 확인도 서빙의 일부가 됩니다. 한 요청의 GPU 계산만 빨라져도 대기열이나 네트워크가 막히면 사용자의 응답은 늦을 수 있습니다.

    한국어판 보충 설명: 모델과 서버는 별개

    모델 파일을 다운로드했다고 해서 서비스가 준비된 것은 아닙니다. 모델의 가중치와 토크나이저를 읽고, GPU 메모리를 확보하고, 요청 형식을 해석하고, 동시 요청을 조정하는 실행 환경이 필요합니다. 소규모 실험에서는 이 일을 한 프로세스가 맡을 수 있지만, 사용자가 늘면 요청 관리와 계산을 나누어 생각하는 편이 문제를 찾기 쉽습니다.

    추론과 서빙은 어떻게 다른가?¶

    추론은 모델이 입력에서 출력을 계산하는 과정입니다. 학습된 가중치를 사용해 다음 토큰의 점수를 만들고, 토큰을 하나 고른 뒤 그 토큰을 다시 입력에 더해 계산을 반복합니다. 이 계산은 노트북이나 단일 Python 프로그램 안에서도 할 수 있습니다.

    서빙은 그 계산을 사용자와 애플리케이션이 안정적으로 이용하게 하는 과정입니다. HTTP API, 요청 대기열, 배칭, 모델 로딩, 상태 확인, 로깅, 부하 분산 등이 여기에 들어갑니다.

    질문 추론에서 보는 것 서빙에서 보는 것
    무엇을 수행하는가? 입력 토큰으로 다음 출력 토큰을 계산한다. 요청을 받고, 계산을 배치하고, 결과를 전달한다.
    성능 문제는? 모델 계산, 메모리 읽기, KV cache 사용 대기열, 동시 요청, 라우팅, 네트워크
    단독 실행이 가능한가? 가능하다. 사용자에게 제공할 실행 경로가 필요하다.

    한국어판 보충 설명: 경계가 겹치는 이유

    실제 제품에서는 한 프로세스가 API를 받고 GPU 계산도 수행할 수 있습니다. 그래서 도구 이름만 보고 둘을 구분하기 어렵습니다. 느린 요청을 분석할 때는 대기열에서 보낸 시간과 모델이 실제 계산한 시간을 나누면 경계가 분명해집니다.

    추론 최적화는 무엇을 바꾸는가?¶

    추론 최적화는 응답을 더 빠르게 보내거나, 같은 하드웨어로 더 많은 요청을 처리하거나, 필요한 메모리와 비용을 줄이는 기법입니다. 단, 속도만 높이고 답의 품질이나 안정성을 잃으면 좋은 최적화라고 할 수 없습니다.

    원문이 소개하는 대표적인 방법은 다음과 같습니다.

    • 연속 배칭: 요청이 끝나는 대로 새 요청을 계산 묶음에 넣어 GPU 빈자리를 줄입니다.
    • KV cache 관리와 prefix caching: 이미 계산한 입력의 일부를 재사용하거나 메모리를 더 효율적으로 관리합니다.
    • 양자화: 모델 가중치의 표현 정밀도를 낮춰 메모리 사용과 계산 비용을 줄입니다. 품질과 하드웨어 지원을 함께 살펴야 합니다.
    • 추측 디코딩(speculative decoding): 작은 모델이 먼저 제안한 토큰을 큰 모델이 검증해 생성 시간을 줄이려 합니다.
    • 병렬화: 모델 또는 요청을 여러 GPU에 나누어 처리합니다. GPU 사이 통신 비용이 생깁니다.

    한국어판 보충 설명: 기법보다 먼저 병목

    첫 토큰이 늦다면 입력 처리와 대기열을, 첫 토큰 뒤의 글이 느리다면 출력 생성과 메모리 사용을 먼저 봅니다. 어느 구간이 느린지 모른 채 기법을 적용하면 비용만 늘 수도 있습니다. 다음 성능 지표 장에서 이 구분을 숫자로 확인합니다.

    API만 사용해도 왜 알아야 할까?¶

    관리형 API를 쓰면 GPU와 서버가 보이지 않습니다. 그래도 응답 시간이 길어지거나 비용이 늘면 입력 길이, 출력 길이, 동시 요청, 스트리밍 여부를 조정해야 합니다. 어떤 지표가 어느 구간의 문제인지 알면 공급자를 비교하거나 자체 서빙을 검토할 때도 질문이 명확해집니다.

    원문은 개발자에게는 빠르고 안정적인 서비스 설계, 기술 책임자에게는 공급자와 자체 운영의 선택, 일반 독자에게는 AI 서비스의 실제 동작을 이해하는 데 이 지식이 유용하다고 설명합니다. 팀의 요구가 커지면 비용, 지연, 맞춤 설정, 데이터 관리 요건 때문에 관리형 API와 자체 서빙을 함께 검토할 수 있습니다. 어느 방식이 낫다는 결론은 요청량과 운영 역량을 함께 본 뒤 내려야 합니다.

    반대로 모델을 직접 운영한다면 GPU 메모리, 대기열, 배칭, 장애 대응까지 책임져야 합니다. 이 책은 계산의 원리에서 시작해 그런 운영 선택으로 이어집니다.

    한국어판 보충 설명: 하나의 요청부터 보기

    처음에는 GPU 종류나 프레임워크 이름을 외울 필요가 없습니다. 질문 하나를 보내고, 첫 토큰이 언제 왔는지, 마지막 토큰이 언제 왔는지, 몇 토큰이 생성됐는지부터 기록하세요. 이 세 값만 있어도 뒤에서 배울 TTFT, E2EL, TPOT를 계산할 수 있습니다.

    핵심 정리¶

    • 추론은 학습된 모델이 입력에서 출력을 계산하는 과정입니다.
    • 서빙은 그 계산을 여러 사용자가 안정적으로 이용하도록 요청을 관리하는 과정입니다.
    • 추론 서버는 모델 로딩, 요청 접수, 실행, 응답 전달을 연결합니다.
    • 최적화 기법은 서로 다른 병목을 다루므로 먼저 느린 구간을 찾아야 합니다.
    • 관리형 API 사용자도 요청 길이와 지연 지표를 알면 비용과 경험을 개선할 수 있습니다.
