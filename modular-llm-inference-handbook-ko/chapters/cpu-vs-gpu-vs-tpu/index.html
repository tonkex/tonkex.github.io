    LLM 추론은 어디에서 실행할까?¶

    작은 모델을 노트북에서 시험할 때와 여러 사용자가 동시에 긴 답을 받는 서비스를 운영할 때는 필요한 장비가 다릅니다. CPU, GPU, TPU 중 무엇이 좋다는 단일 순위보다 모델이 메모리에 들어가는지, 요청이 얼마나 몰리는지, 응답을 얼마나 빨리 받아야 하는지가 먼저입니다.

    이 장은 Modular의 Where is LLM inference run?을 번역·재구성했습니다. 기준 원고는 커밋 07e93d6입니다. 하드웨어의 우열과 비용에 관한 단정은 모델·장비·소프트웨어·작업 부하에 따라 달라지므로 한국어판 보충 설명에서 조건을 명시합니다.

    CPU: 접근하기 쉽지만 언제 한계에 부딪힐까?¶

    CPU(Central Processing Unit)는 대부분의 컴퓨터와 서버에 있는 범용 처리 장치입니다. 조건 분기, 데이터 준비, 네트워크 처리 등 다양한 작업을 잘 다룹니다. 작은 모델을 로컬에서 시험하거나 요청이 드문 서비스라면 CPU로 시작할 수 있습니다.

    큰 LLM은 여러 행렬 연산을 반복합니다. CPU도 이 계산을 할 수 있지만, 일반적으로 같은 작업에 맞는 가속기를 쓸 때보다 동시 처리량이 낮고 답변이 늦을 수 있습니다. 특히 긴 답변을 많은 사용자에게 동시에 제공하려면 CPU만으로는 목표 지연 시간을 맞추기 어려울 수 있습니다.

    한국어판 보충 설명: CPU 추론이 쓸모없는 것은 아닙니다

    CPU는 모델이 작거나 충분히 양자화됐고, 트래픽이 적으며, 별도의 GPU를 확보하기 어려운 환경에서 합리적일 수 있습니다. 서버의 요청 접수·토큰화·후처리도 CPU가 맡는 경우가 많습니다. 성능 판단은 “CPU냐 GPU냐”라는 이름만으로 하지 말고 같은 모델·입력·출력 길이에서 TTFT와 처리량을 재야 합니다.

    GPU: 왜 많은 LLM 서빙 시스템의 기본 선택일까?¶

    GPU(Graphics Processing Unit)는 원래 그래픽 계산에 쓰였지만, 많은 숫자에 비슷한 연산을 동시에 적용하는 데 강합니다. Transformer의 행렬 곱셈과 텐서 연산이 이런 병렬 계산을 활용합니다. 원문은 GPU를 생성형 AI 학습과 추론의 보편적인 선택으로 소개합니다.

    GPU에는 가중치와 KV 캐시를 올릴 VRAM이 있습니다. GPU 연산 능력이 충분해도 모델과 실행 중 메모리가 VRAM에 들어가지 않으면 그 구성으로는 바로 서빙할 수 없습니다. 메모리 계산 장의 예산을 먼저 확인하고, 그다음 같은 조건에서 첫 토큰 지연·토큰 생성 속도·동시 요청 처리량을 측정하세요.

    vLLM, SGLang, MAX, LMDeploy, TensorRT-LLM, Hugging Face TGI 같은 서빙 소프트웨어는 GPU 가속을 활용합니다. 다만 사용 가능한 GPU 제조사, 정밀도 형식, 커널, 운영체제와 설치 방법은 프레임워크 버전에 따라 다릅니다.

    • Modular 원문: GPU 선택 — 모델·메모리·장비 선택의 다음 단계.

    TPU: 특화된 가속기는 언제 고려할까?¶

    TPU(Tensor Processing Unit)는 Google이 기계학습의 텐서 연산을 위해 설계한 가속기입니다. Google Cloud 문서에서는 TPU를 학습과 추론에 사용할 수 있으며, 대규모 행렬 계산을 수행하는 구조와 소프트웨어 환경을 설명합니다. 원문은 TPU가 추천 시스템, 생성형 모델 등 여러 Google 서비스에도 사용된다고 소개합니다.

    TPU를 검토한다면 먼저 원하는 모델과 연산이 해당 TPU 세대에서 지원되는지, 사용하는 프레임워크가 XLA·JAX·PyTorch/XLA 등을 통해 필요한 기능을 제공하는지 확인해야 합니다. 클라우드 리전, 예약 가능 용량, 실행 시간과 전송 비용도 선택에 영향을 줍니다.

    한국어판 보충 설명: ‘TPU가 GPU보다 빠르다’는 조건부 주장입니다

    원문 표는 TPU를 텐서 연산에 매우 효율적인 장치로 단순 비교합니다. 그러나 특정 LLM의 첫 토큰 지연, 출력 처리량, 전력 효율에서 어느 장치가 앞서는지는 장비 세대, 모델, 배치 크기, 정밀도, 커널, 서빙 엔진에 따라 달라집니다. 같은 조건의 측정 결과 없이 모든 TPU가 모든 GPU보다 빠르다고 결론 내릴 수 없습니다.

    하드웨어를 고를 때 무엇을 비교할까?¶

    원문은 CPU의 범용성, GPU의 폭넓은 병렬 처리, TPU의 텐서 연산 특화를 나란히 보여 줍니다. 아래 표는 절대적인 성능 순위가 아니라 첫 후보를 좁히는 안내입니다.

    질문 CPU GPU TPU
    주된 성격 범용 계산 장치 대규모 병렬 계산 가속기 텐서 연산에 특화된 가속기
    먼저 고려할 때 작은 모델, 낮은 트래픽, 로컬 실험 일반적인 LLM 학습·서빙 지원되는 모델을 TPU 환경에서 대규모로 실행할 때
    주로 쓰는 메모리 시스템 DRAM GPU의 GDDR 또는 HBM 등 TPU 세대별 가속기 메모리
    소프트웨어 확인점 CPU 커널과 양자화 지원 GPU 제조사·드라이버·커널 지원 XLA 계열의 모델·연산 지원
    흔한 제약 큰 모델의 지연·처리량 VRAM 용량, 장비 비용·공급 모델 호환성, 이용 가능한 인프라

    실제 선택에서는 다음 순서가 유용합니다. ① 모델과 정밀도를 정하고 ② 가중치·KV 캐시의 메모리를 계산하고 ③ 입력·출력 길이와 동시 요청 수를 정한 뒤 ④ TTFT·TPOT·Goodput과 비용을 같은 조건에서 비교합니다. 단가만 비교하면 요청 하나를 완료하는 데 필요한 시간이나 실패율을 놓칠 수 있습니다.

    한국어판 보충 설명: 원문 비교표의 경향을 읽는 법

    원문에는 CPU·GPU·TPU의 메모리 대역폭, 지연, 전력 효율, 비용을 낮음/높음으로 표시한 항목이 있습니다. 실제 수치는 제품과 구성에 따라 겹치며, CPU 코어 하나의 지연과 GPU 배치의 지연은 같은 단위의 공정한 비교가 아닙니다. 후보 장비의 공식 사양과 실제 모델 벤치마크를 함께 확인하세요.

    어디에 배포하느냐도 함께 결정해야 할까?¶

    같은 모델과 장비라도 클라우드, 자체 데이터센터, 사용자 기기 중 어디에서 실행하느냐에 따라 지연, 관리 책임, 데이터 흐름, 비용 구조가 달라집니다. 원문은 다음 다섯 가지 배포 방식을 소개합니다.

    배포 방식 무엇을 뜻하나? 주로 확인할 점
    클라우드 공급자의 가속기와 관리형 서비스를 필요할 때 사용한다. 리전·용량·요금·데이터 경로
    멀티클라우드·다중 리전 여러 공급자나 지역으로 요청을 나눈다. 라우팅·복잡성·데이터 거주 요건
    BYOC(Bring Your Own Cloud) 공급자 소프트웨어를 내 클라우드 계정 안에서 실행한다. 계정·네트워크·운영 책임의 경계
    온프레미스 자체 데이터센터의 장비를 운영한다. 장비 확보·장애 대응·유지비
    엣지·온디바이스 사용자 기기나 데이터 발생 지점 가까이 실행한다. 메모리·전력 제한·오프라인 요구

    원문은 클라우드의 탄력성과 관리 도구, 멀티클라우드의 지역 선택과 공급자 분산, BYOC의 계정 내부 통제, 온프레미스의 직접 관리, 엣지의 네트워크 지연 감소를 각각 장점으로 설명합니다. 동시에 어느 방식이든 보안·규정 준수나 비용이 자동으로 해결되지는 않습니다. 예를 들어 BYOC를 선택해도 누가 모델 서버를 패치하고 장애에 대응하는지 계약과 설계에서 확인해야 합니다.

    핵심 정리¶

    • CPU는 작은 모델과 낮은 요청량에서 유용하며, 큰 LLM 서비스에서는 성능을 확인해야 합니다.
    • GPU는 많은 LLM 서빙 시스템의 보편적인 선택이지만 VRAM·정밀도·커널 지원이 중요합니다.
    • TPU는 텐서 연산에 특화됐으며 모델과 소프트웨어의 호환성을 먼저 확인해야 합니다.
    • 장비의 절대적인 우열보다 같은 작업 부하에서의 지연·처리량·비용이 중요합니다.
    • 클라우드, BYOC, 온프레미스, 엣지는 운영 책임과 데이터 경로까지 함께 결정합니다.
